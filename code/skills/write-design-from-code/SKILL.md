# 基于已审查代码生成设计说明

## 目标与交付性质

供任意能够读取文本和代码的大模型智能体使用，不依赖特定工具或厂商。生成的是**基于指定代码基线还原的现状设计说明**，不是事前批准的目标设计，也不是代码正确性或安全认证证明。

设计说明应让读者理解组件如何协作、数据和状态如何变化、接口和异常如何处理，以及哪些结论有证据。不要只把文件名和函数签名翻译成自然语言。

## 输入与配套文件

必需输入：第一项审查的交接报告、报告所指代码及配置、拟说明范围。可选输入：需求、接口约定、原设计、决策记录、模型、测试和分析证据。

- 阅读 [设计说明模板](references/design-template.md)。
- 核验报告时阅读 [交接报告约定](../review-code-for-design/references/handoff-report.md)。这是显式的配套依赖，分发时应保留两个 skill 目录的相对位置，或一并提供约定内容。
- 若需先行或重新审查，使用 [review-code-for-design](../review-code-for-design/SKILL.md)；不得伪造一份通过报告。
- 验证本 skill 时使用 [行为验收场景](references/acceptance-cases.md)。

默认输出 Markdown，不使用 HTML。已有用户指定模板时，保留其组织方式，同时补足基线、证据和限制字段。只有在用户要求写文件且位置明确或可以合理确定时才落盘；不修改产品代码，不覆盖未经授权的既有文档。

## 1. 先检查生成准入

1. 报告不存在时，先完成第一项审查；若代码或相应指令不可取得，说明所缺内容并停止正式生成。
2. 核对报告身份、允许范围、限制、开放问题，以及代码、未提交修改、未跟踪工件和实际配置。
3. 报告与代码有差异时，先评估变化并复查受影响范围，更新交接结果；不能只因提交号相同就默认一致。
4. 无法核验基线时，不声称匹配。取得可核验材料或对当前材料重新审查后再生成。
5. `READY` 可生成对应范围的说明。`LIMITED` 仅生成明确允许部分，醒目标明局部说明和遗漏边界；若用户必须要完整说明，先解决限制。`BLOCKED` 只输出阻断项和补充材料要求，不生成看似完整的正式说明。

被允许文档化不代表问题已修复。所有影响文档结论的开放问题必须继承，不得省略。

## 2. 建立主张与证据表

重新阅读支撑关键章节的代码和配置，不能只把第一份报告改写成设计说明。记录每个重要设计主张对应的文件、符号、配置或报告来源。

采用四种证据标签，可按段落或表项标记，不必逐句重复：

- **实现事实**：由所审代码、配置直接支持。
- **运行观察**：由已执行活动支持，写明环境、版本与观测范围。
- **推断**：说明推导依据和未排除的其他解释。
- **未知／待确认**：材料不足，不能作出结论。

要求、注释和测试预期分别表述为其所声明的内容，不自动等同于实现事实。发生不一致时并列记录，不擅自选一方为真。

## 3. 按实际实现构建设计视图

- 说明系统边界、启动与装配方式，区分编译期和运行期配置。
- 按真实职责组织组件，而非机械逐文件列清单；说明逻辑组件与文件、符号的映射。
- 说明接口的调用者、被调用者、输入输出、所有权、副作用和错误约定。
- 说明关键数据、状态、生命周期、共享与同步；存在多种运行变体时分开说明。
- 对关键场景展示执行顺序、分支、状态变化及异常路径。
- 对算法说明输入、步骤、内部状态和数值边界；缺少公式来源时不补造理论依据。
- 区分第三方库的可见契约和无法读取的内部实现，不推演黑盒细节。

图或表仅在关系复杂时使用。每条重要连接都应有证据；无法确认的动态连接标为未知，不用架构图掩盖缺口。图中名称和正文、代码映射一致。

航空航天软件还应按实际范围说明模式、控制权限、坐标与时间语义、任务周期、故障处理、参数与生成链、平台接口。源代码常量只能证明配置或计算规则，不能证明实际实时性、控制性能或安全性。

## 4. 保留现状、问题和建议之间的边界

- 正文如实描述现状，包括明确的缺陷行为；把风险、偏差与改进建议单列并关联问题编号。
- 设计理由只能来自可追溯决策记录或明确资料。代码通常说明“做了什么”，不能单独证明“为什么选择这样做”。
- 不把变量名称猜成需求，不创建虚假的需求编号；没有需求时，注明需求符合性未核对。
- 不把未执行的测试写成已通过，不把主机观测推广到目标机或真实设备。
- 缺少论证时，不宣称线程安全、稳定性、容错性、最坏执行时间或特定规范符合性。
- 建议的未来架构放在独立“改进建议”中，不混入现状架构图。

## 5. 生成并自检

使用模板按适用性裁剪。遗漏的必需信息写为未知或限制；不适用章节注明理由，避免空标题堆积。

逐项核对：

1. 基线与准入范围一致，标题是否明确为完整或局部的现状说明。
2. 范围内重要组件、接口和关键执行链是否都有描述。
3. 正文、图表、伪代码中的主要关系是否能回到证据。
4. 所有关键结论是否正确区分事实、观察、推断和未知。
5. 注释与代码冲突、开放问题、范围限制是否保留。
6. 是否把建议、预期或假设误写为已实现机制。
7. 证据链接是否存在且对应当前版本；无工具时明确哪些链接未核验。

生成中发现新的关键结构不确定性时，退回第一项审查并更新准入；不能为完成文档自行补齐。

## 6. 交付与更新

交付设计说明、证据索引和待确认问题；说明覆盖范围、实际检查及未完成项。生成文档不自动代表获得人工批准。

后续代码变更时，先更新审查与影响范围，再更新对应章节和证据。保留基线和修订记录，避免文档仍描述旧代码却使用新版本标题。
