# 基于需求设计系统级测试用例

## 目标与输入

供任意大模型智能体使用，不依赖特定工具。默认交付测试规格和追溯矩阵，不实施测试、不修改需求或产品。

必需材料是需求正文或受控位置、版本和待验证系统范围。任务场景、接口、配置、危险分析、操作约束、需求审查报告及验证计划可作为补充。

阅读 [系统测试规格与交接模板](references/test-specification.md)。验证本 skill 时可用 [行为验收场景](references/acceptance-cases.md)。

需求审查结论是有用输入，但不能仅凭“审查通过”跳过对用例相关条款的阅读。发现歧义时记录问题，可使用已有需求审查流程；未提供相关 skill 不妨碍本 skill 提出局部缺口。

## 1. 定义待测系统与证据范围

明确系统包含哪些软件、硬件、外部服务或模拟对象，哪些接口是观测边界。记录需求、接口、参数和候选系统配置的版本。

“系统级”由被测边界和端到端义务决定，不由是否使用某个测试工具决定。SIL 或 HIL 可以承载指定范围的系统测试，但不能据名称推断已覆盖完整实际系统。

对多种构型、任务阶段或运行环境，说明分别测试或采用代表配置的依据，不能无依据地从一个配置推广到全部配置。

## 2. 从需求提取验证义务

逐条提取触发条件、允许与禁止行为、前提、时间和质量约束、异常与恢复规则、验收判据及引用来源。将复合需求拆为可追溯的验证义务，不改变其含义。

区分用测试、分析、审查或演示验证的内容。不能仅用测试证明的要求，标明其他证据需求，不硬凑一个测试后声称完全覆盖。

缺少阈值、时间起止点、运行范围或故障策略时，阻断受影响用例并提出可回答的问题；不要由现有代码或常见实践反向替用户决定需求。

## 3. 设计端到端场景

从真实外部输入和初始状态出发，经被测系统实际链路到外部可观察结果，包括适用的正常任务、边界、无效输入、故障、降级、恢复、权限、资源竞争和长时运行。

建立“阶段／模式 × 输入类别 × 故障 × 时间边界 × 配置”的场景视图，按重要性和风险选择组合，说明未覆盖部分，不宣称已穷举。

系统测试的通过判据应来自需求或明确的独立依据。内部探针可帮助诊断，但不能用某个内部函数执行成功替代端到端结果。探针的时间、资源和行为影响也需说明。

## 4. 定义可信的测试环境

为每个场景明确真实组件、模拟组件、模型和版本、外部依赖、时间同步、测量精度、数据采集、资源与负载条件。

模型必须有适用范围和所需可信度依据。模型超出范围时，不应安排为正式符合性证据；可另列探索场景。参考模型与产品模型共享错误的可能性需标为限制。

涉及实物、故障注入或设备动作时，写明待批准的程序、允许注入范围、互锁、中止条件和恢复要求。设计用例不构成试验执行或飞行授权。

## 5. 写出可判定、可复现的用例

规定起始状态、输入历史、刺激与注入时刻、步骤、观测变量、指标计算、窗口与容差、退出及清理。依赖计时的要求必须说明起算与结束事件。

统计或随机试验应明确总体或分布、相关性、抽样策略、种子、样本或停止规则以及判断依据。没有批准的统计标准时只能列候选方案，不能自动设计“跑到通过为止”的试验。

多次成功或大量随机样本不证明全部状态空间正确。不能凭观测数据的最大值声称得到理论最坏上界。

## 6. 航空航天专项

按范围加入任务阶段和飞行包线、模式与控制权限、测量源有效性、源采样时标、传感器及执行机构故障、组合故障、切换瞬态、数值与实时约束、控制性能和环境不确定性。

性能指标、允许偏差、故障策略和试验边界必须来自项目资料，不能自行指定。真实目标机、实时仿真、模型和测量链路分别说明证据能力。

飞行试验之外的试验也可能涉及危险设备；本 skill 只设计，不驱动设备、不解除互锁、不扩大获准试验范围。地面软件同样应考虑指令权限、时效、防重放及操作记录等适用要求。

## 7. 检查追溯并交付

建立“需求条款—验证义务—用例—判据—环境与限制”矩阵；区分已设计覆盖、可执行覆盖和未来执行证据。关键要求若只能部分验证，标明剩余方法与证据，不写成全部覆盖。

用例使用 `DRAFT`／`READY`／`BLOCKED`。`READY` 指用例规格完备，不代表设备试验已获批准。交付测试集、覆盖与缺口、环境前提、执行记录要求和需求澄清问题。
