# 运行需求驱动的一致性与验证闭环

## 目标与使用边界

本 skill 负责组织整个工作流、选择下游专项 skill、维护基线与问题状态，并在每个阶段给出可继续、需人工决定或证据不足的判断。它不重复各专项 skill 的详细检查规则，也不自动批准需求、修改受控工件、放宽判据或发布产品。

适用于新功能、变更、缺陷修复、遗留系统补文档和阶段性审查。可覆盖完整产品，也可针对一个边界清楚的功能增量运行；范围越小，越要明确与未审部分的接口和影响。

开始时读取 [工作流记录模板](references/workflow-record.md)。调试或验证本 skill 时读取 [行为验收场景](references/acceptance-cases.md)。只加载当前阶段需要的专项 skill，不必一次把所有配套引用载入上下文。

## 不可破坏的闭环原则

1. **先固定问题和基线，再改变工件。** 记录需求、设计、代码、参数、构建、测试及证据版本；保留旧失败和旧基线。
2. **上游意图不能由下游现状反向决定。** 代码已有行为、测试当前预期或修复便利性不能自动成为需求依据。
3. **正向与反向追溯都要成立。** 正向检查上游义务是否落实；反向检查下游行为是否有依据。
4. **审查结论与批准决定分开。** 智能体整理事实、偏差、方案和影响；授权人决定业务价值、安全策略、阈值、风险接受和基线变更。
5. **问题回到正确工件。** 需求问题改需求，设计问题改设计，实现问题改代码，测试问题改测试，环境或证据问题修复环境与采集；不能为“变绿”随意改另一层。
6. **修复不等于关闭。** 只有变更获准、写入受控工件、影响分析完成、原反例与必要回归通过且证据有效，问题才可关闭。

## 阶段 0：建立范围、角色和证据台账

记录任务目标、产品边界、适用配置、生命周期阶段、待处理变更、输入工件及版本。识别系统或业务负责人、需求负责人、设计与实现负责人、验证负责人、配置与变更负责人，以及适用的独立审查要求。

明确哪些动作只读，哪些会修改工件、运行代码、连接设备或影响外部系统。用户要求“走完整流程”不自动授权所有写入和执行；对未授权步骤形成待办和所需输入。

建立贯穿全程的主链：

**目标与约束 → 需求 → 设计、模型与参数 → 代码与构建 → 验证义务与用例 → 执行证据 → 问题与决定 → 新基线与回归证据。**

## 阶段 1：判断需求是否合理且足以进入设计

需求合理性不等于文字完备。对每项关键需求检查：

- 是否追溯到明确的任务目标、用户需要、系统分配、法规合同、接口保证、危险控制或获准决策。
- 是否确有必要，是否与其他目标重复或冲突，是否把某种实现方案误写成唯一需求而没有依据。
- 在给定技术、资源、时间、环境和运行范围内是否有可行性证据；缺少专业分析时标为待确认，不能凭直觉断言可行。
- 收益、代价、故障后果、替代方案和残余风险是否由有权角色理解并接受。
- 是否能定义实现与验证边界，是否存在无法观测、阈值无来源或依赖不受控等问题。

再使用 [review-requirements](../review-requirements/SKILL.md) 检查完备性、实质歧义、矛盾和可验证性。把两类结论分开：

- **质量结论**：文本是否足以被一致理解和验证。
- **合理性建议**：现有证据是否支持其目标、必要性、可行性和风险取舍。
- **人工决定**：`APPROVE`／`REVISE`／`REJECT`／`DEFER`，必须记录决定人、依据和适用范围。

关键需求存在无来源阈值、未决故障策略、明显冲突或不可接受的可行性未知时，状态为 `HOLD`。允许原型探索时必须标为非符合性活动，不能把原型结果冒充已批准需求。

## 阶段 2：建立需求基线并形成设计

只有获准范围进入需求基线。设计应说明组件与接口、状态与执行链、算法和参数、异常恢复、并发与时序、资源、配置变体及验证观察点。模型、生成配置和参数若会改变行为，也作为受控设计产品。

设计中出现新的外部行为、阈值、时间预算、模式或故障策略时，将其登记为派生需求候选，反馈系统、领域和安全负责人确认；不得仅以“实现需要”为由静默加入。

本仓库没有“从需求直接生成目标设计”的专项 skill。可按用户指定方法编写或审查设计，但必须保存依据、假设与未知。对于只有代码而缺少可信设计的遗留系统，走例外分支：

1. 用 [review-code-for-design](../review-code-for-design/SKILL.md) 判断代码是否足以被可靠说明。
2. 用 [write-design-from-code](../write-design-from-code/SKILL.md) 生成带证据标签的**现状设计说明**。
3. 明确该说明不是已批准目标设计，再与需求比对并由负责人决定修代码、修文档还是补充上游决定。

## 阶段 3：验证需求与设计一致

使用 [compare-requirements-to-design](../compare-requirements-to-design/SKILL.md) 建立双向追溯：

- 正向确认每项适用需求义务均被设计机制落实。
- 反向确认关键设计承诺有需求、接口或获准决策依据。

`INCONSISTENT` 或涉及关键义务的 `UNKNOWN` 时暂停受影响实现。`PARTIALLY_CONSISTENT` 只允许明确划出的独立范围继续，不能把局部一致写成整体通过。

若问题源于需求，返回阶段 1；若源于设计，返回阶段 2；若只是缺失引用或版本不匹配，先补齐证据，不要修改产品语义。

## 阶段 4：实现并验证设计与代码一致

实现活动必须绑定已批准设计、配置和变更范围。代码、模型、生成物、参数、依赖、编译开关与目标构建共同构成实现基线，不能只记录提交号。

使用 [compare-design-to-code](../compare-design-to-code/SKILL.md) 检查设计义务是否实现及实现行为是否有设计依据。代码中发现设计未规定但影响外部行为的机制时，不能直接把文档改成与代码一致；先判断是合法实现细节、设计遗漏、派生需求还是无依据实现，并交相应负责人决定。

明确冲突、关键遗漏或无法确认实际构建时，对受影响范围标记 `HOLD`。静态一致性不能证明实时上界、硬件交互、控制性能或全部运行路径正确。

## 阶段 5：独立设计验证并取得执行证据

尽量让测试预期来自已批准需求、设计、独立推导或可信参考，而不是复制产品代码。按验证层次路由：

- 使用 [design-unit-tests](../design-unit-tests/SKILL.md) 从设计义务产生单元测试规格。
- 使用 [design-system-tests](../design-system-tests/SKILL.md) 从需求产生端到端系统测试规格。

集成测试、分析、审查、模型验证、目标机时序和硬件试验按项目要求补充；现有 skill 未覆盖时，记录方法、责任人和证据要求，不用单元或系统测试名称掩盖缺口。

执行前固定 RUN 清单、代码或二进制、配置、环境、用例、判定程序和数据采集版本。涉及实物、故障注入或飞行活动时，必须有独立的操作授权、互锁和中止条件；测试设计或本工作流不构成执行许可。

## 阶段 6：评估证据而不是只看测试汇总

使用 [evaluate-unit-test-results](../evaluate-unit-test-results/SKILL.md) 和 [evaluate-system-test-results](../evaluate-system-test-results/SKILL.md) 检查实际执行是否有效、判据是否适用、结果是否支持对应义务。

分别记录执行有效性、断言结果、稳定性、环境代表性和覆盖范围。没有原始证据、配置不匹配或测试未发现时，不把框架的绿色汇总作为符合性通过。

把结论限制在实际版本、配置、场景和环境内。单元、主机、仿真或台架通过不能自动推广到目标机、全运行范围、安全性或发布批准。

## 阶段 7：分类问题并触发人工决策

先找到最早偏离预期的位置，再提出候选根因。问题至少分到以下工件或责任域：

| 类别 | 默认反馈对象 | 典型处理 |
| --- | --- | --- |
| 目标、需求或安全策略 | 系统、需求、领域或安全负责人 | 澄清、重分配、修订、拒绝或接受残余风险 |
| 设计、模型或参数 | 设计、控制或模型负责人 | 修订机制、依据、适用范围或参数基线 |
| 代码、构建或平台 | 软件负责人 | 修复实现、构建配置或平台集成 |
| 测试、判据或替身 | 验证负责人 | 修订用例、独立预期或测试实现 |
| 环境、台架或采集 | 试验与环境负责人 | 恢复有效环境、校准或重采证据 |
| 证据不足或根因未知 | 对应负责人共同评审 | 最小区分试验、补充材料或受控复现 |

智能体可以提出多个处理方案，并为每个方案说明受影响工件、收益、代价、风险和回归范围；不得替授权人选择安全策略、业务取舍或风险接受。

需要改变已批准行为时，状态设为 `READY_FOR_HUMAN_DECISION`，等待授权人给出 `APPROVE_CHANGE`／`REJECT_CHANGE`／`REQUEST_ANALYSIS`／`DEFER`。决定必须进入受控记录；口头或聊天答复在写回基线前只能标为“决定已明确，文档待更新”。

## 阶段 8：受控变更、影响分析与回归关闭

对获准变更建立唯一标识，保存问题证据、决定依据、修改工件、责任人和新版本。沿双向追溯分析上下游影响：父子需求、接口、设计组件、代码路径、模型参数、构建变体、测试预期和既有通过证据。

按变更类型回到最早受影响阶段，而不是永远只重跑失败用例：

- 需求改变：从阶段 1 或 2 重新进入，并使依赖旧需求的设计、代码和验证证据待复核。
- 设计改变：重新做需求—设计和设计—代码一致性，并更新相关测试。
- 代码或构建改变：重新做设计—代码一致性，运行原反例及影响范围回归。
- 测试或环境改变：保留原结果，重新确认判据和环境有效性后执行受影响用例。

问题关闭必须同时满足：批准决定已写入受控工件；相关基线一致；原反例不再出现或已由获准新需求重新定义；必要回归与证据评估完成；残余限制和未覆盖范围已记录。否则保持开放、待复查或保留限制。

## 阶段 9：阶段结论与持续反馈

阶段结论使用：

- `READY`：本阶段适用门槛满足，证据和批准记录齐全，可进入下一阶段。
- `READY_WITH_LIMITS`：只允许明确范围继续，限制不影响该范围且有责任人和关闭条件。
- `HOLD`：存在明确冲突、关键义务缺失、未获批准的行为改变或无效证据。
- `INDETERMINATE`：关键版本、范围、引用或证据不足，尚不能判断。

`READY` 不是产品发布、安全认证或飞行批准。最终验收由项目定义的授权人根据全部适用证据和未关闭问题决定。

交付工作流记录、阶段门状态、双向追溯索引、问题与人工决定、变更影响、验证证据和下一步动作。运行反馈、新缺陷或环境变化重新进入阶段 0，形成新一轮受控闭环，不覆盖上一轮历史。
