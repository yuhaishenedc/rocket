# 代码审查到设计说明的交接约定

此约定定义第一项 skill 的输出和第二项 skill 的输入。报告使用 Markdown 即可，不要求专用服务或解析器。字段缺失时明确标记，不填写虚构内容。

## 1. 报告身份与准入结论

- 约定版本：1。
- 报告标识与审查日期：
- 结构质量结论：主要优点、结构问题、尚不能判断的部分。
- 生成准入状态：`READY`／`LIMITED`／`BLOCKED`。
- 状态依据：
- 允许生成范围：明确组件、行为及配置。
- 禁止或暂缓生成范围：以及需补充的证据。

准入仅针对现状文档生成，不代表软件可发布、满足需求、安全合格或通过认证。

## 2. 代码基线

| 项目 | 内容 |
| --- | --- |
| 仓库或材料包 | 位置或标识 |
| 版本 | 提交号、发布标签或材料包版本 |
| 工作区差异 | 修改与未跟踪文件清单，或明确未知 |
| 快照依据 | 可用的文件摘要、归档标识或其他核验方法 |
| 构建配置 | 平台、功能开关、目标、关键依赖及配置来源 |
| 无法核验项 | 具体事项与对结论的影响 |

## 3. 阅读范围与结构证据

| 组件或文件 | 已读范围 | 职责与关键符号 | 入口和依赖 | 状态归属 | 证据定位 |
| --- | --- | --- | --- | --- | --- |

另列未读文件、外部黑盒、生成工件及被排除变体，说明理由。关键证据至少记录文件相对路径、符号、关联配置和必要的行号；仅有行号不足以应对后续漂移。

## 4. 关键执行链

| 场景 | 起点与前提 | 调用或事件顺序 | 数据与状态变化 | 输出或副作用 | 证据及未知 |
| --- | --- | --- | --- | --- | --- |

覆盖范围内的重要正常和异常链路。不存在或不适用的并发、恢复等机制应说明，不补造机制。

## 5. 问题清单

每项使用稳定编号，例如 CODE-001，并记录：

- 类型：结构问题／证据缺口／疑似行为缺陷／已观察缺陷／表达问题。
- 文件、符号、配置及证据；注明静态推导还是实际执行所得。
- 具体问题、触发条件或反例；依赖的尚未确认假设。
- 对理解、实现或验证的影响。
- 对文档的影响：可如实描述／局部限制／阻断关键说明。
- 最小处理建议、建议负责人和关闭所需证据。
- 状态：开放／已处理待复查／关闭／保留限制。

不要把建议的重构方案当成代码已经具有的架构。

## 6. 检查活动与限制

列出实际阅读、实际执行的工具及结果、未执行的分析或测试。没有执行的命令仅能列为建议；不要出现“预计通过”冒充结果。

## 7. 交给设计说明生成者

- 应描述的组件、接口、执行链和配置。
- 必须保留的问题编号和限制。
- 可以描述的事实、需标记为推断的事项、必须保留未知的事项。
- 若用户要求完整文档，当前还需关闭的缺口。
- 下次代码变化后需重新审查的内容。
