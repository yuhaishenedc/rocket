# 面向飞行控制及航空航天软件的需求、实现与验证闭环方案

## 1. 目标、范围与边界

本方案以飞行控制软件为主要场景，建立从需求规格说明、设计与代码、测试生成与执行，到结果分析和变更反馈的开发闭环。同时保留可裁剪结构，用于航天器姿态控制、机载数据处理、航电通信、任务管理、地面测控和试验支持软件。

这里有两种不同的“闭环”：

- **开发闭环**：发现问题，定位原因，修改受控工件，重新验证。
- **控制闭环**：测量、状态估计、控制计算、执行机构和飞行器动力学之间的反馈。

开发闭环必须验证控制闭环，但一次仿真通过并不意味着软件可以投入飞行。需要分别回答：

1. 需求是否正确表达任务意图、系统约束和故障处置要求？
2. 软件设计、代码、参数及目标机行为是否符合已确认需求？
3. 模型、测试预期、执行环境和结果证据是否可信？
4. 集成后的系统是否在规定任务条件和适用范围内满足性能与安全要求？

本文件是工程实施方案，不是适航符合性声明。项目应先确定适用规范、软件分级、验证独立性、交付证据和审批权限，再裁剪流程。例如 FAA AC 20-115D 涉及特定机载系统与设备软件的适航符合性方法，并认可 DO-178C 等文件；不能把它直接当作所有航空航天软件的统一要求。[FAA AC 20-115D](https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_20-115D.pdf)

NASA 项目应按其适用的软件工程与软件保证要求建立项目实施计划；其他航空航天项目应依据各自主管机构、合同和项目规定确定适用性。[NASA 软件工程要求与标准资料入口](https://www.nasa.gov/intelligent-systems-division/software-management-office/nasa-software-engineering-procedural-requirements-standards-and-related-resources/)

以下流程、模板和示例为本方案的设计建议；不应将其误认为上述规范的逐条转述。

## 2. 闭环总览与职责

### 2.1 工作流程

~~~mermaid
flowchart TD
    A[任务目标、系统需求、运行范围与危险分析] --> B[软件需求、接口与参数约束]
    B --> C[人和智能体分别理解并进行场景审查]
    C --> D{本阶段需求是否可接受}
    D -- 否 --> E[登记缺口并由授权负责人决策]
    E --> B
    D -- 是 --> F[建立需求基线]
    F --> G[设计、模型、代码与目标构建]
    F --> H[独立制定验证方法、测试场景与预期]
    G --> I[审查、分析及分层测试]
    H --> I
    I --> J[证据归集与自动分析]
    J --> K{问题分类}
    K -- 需求或系统约束 --> E
    K -- 设计或实现 --> G
    K -- 模型参数或接口 --> L[相应负责人修订并评估影响]
    L --> B
    K -- 测试或试验环境 --> M[修正测试或环境并重新执行]
    M --> I
    K -- 证据不足 --> N[补充测量和受控复现]
    N --> J
    K -- 满足阶段条件 --> O[阶段验收与证据归档]
    O --> P[下一层集成及运行反馈]
    P --> B
~~~

“基线”是经过确认并具有唯一版本标识的一组工件。发现问题后建立新基线，不覆盖旧需求、旧测试结果和失败证据。

### 2.2 责任划分

| 角色 | 主要责任 |
| --- | --- |
| 系统与任务负责人 | 确认任务目标、运行范围、系统分配、模式与控制权限 |
| 控制与领域负责人 | 确认算法、控制性能、模型适用性、数值和参数依据 |
| 软件负责人 | 需求落实、架构、实现、目标环境与资源约束 |
| 安全与保证人员 | 审查危险关联、验证充分性、独立性及残余问题 |
| 验证与试验负责人 | 制定独立预期，管理测试方法、台架和证据有效性 |
| 配置与变更负责人 | 基线、影响分析、批准记录和交付一致性 |
| 智能体 | 辅助查漏、生成候选设计和测试、运行获准任务、整理证据及提出归因假设 |

角色可以按项目规模配置，但不能因此取消项目要求的独立审查。让同一个智能体先写代码再换身份审查，不自动构成合格的验证独立性。

## 3. 如何确认需求对人和智能体足够完备

### 3.1 完备性不是“文字很多”，而是关键决策无需猜测

不能仅凭文档检查证明需求绝对完备。本方案采用**在明确范围内可评审、可实施、可验证的完备性**：

- 范围已知：任务阶段、飞行包线或运行范围、软硬件配置、故障假设和外部依赖明确。
- 对范围内的重要情境，能够确定应执行的行为、执行时机、约束和可观察结果。
- 对超出范围或尚未决定的事项，明确标为限制、假设或待决问题，而不是由实现者自行补齐。

从人的视角，要能解释“为什么这样做、异常时怎么办、后果由谁承担”。从智能体的视角，要能从文档中提取一致的条件、状态、动作、时序和判定标准，不能依赖此前聊天中的隐含背景。

人和智能体得到相同解释只是检查手段，不是真实性证明：两者可能共享同一种错误假设。因此还要用系统分配、领域分析和反例检查需求。

### 3.2 航空航天需求检查维度

| 维度 | 规格说明必须回答的问题 |
| --- | --- |
| 任务与运行范围 | 哪些飞行阶段或任务阶段适用？允许的环境、初始条件与运行边界是什么？ |
| 模式与权限 | 有哪些模式？谁能切换？转移条件、优先级、冲突仲裁和禁止转移是什么？ |
| 信号语义 | 单位、坐标系、轴向、正负号、姿态表示、时间基准和精度是什么？ |
| 数据有效性 | 数据存在是否代表有效？如何处理陈旧、失序、重复、缺失和质量标志异常？ |
| 实时性 | 采样、计算、发布各是什么周期？端到端截止时间、抖动及多速率关系是什么？ |
| 初始化与恢复 | 上电、复位、重启、状态恢复和热切换时，内部状态及输出如何处理？ |
| 数值行为 | 浮点或定点范围、舍入、溢出、非有限值、离散化和累计误差如何约束？ |
| 执行机构约束 | 饱和、速率限制、死区、不可用及指令反馈不一致如何处理？ |
| 故障与降级 | 检测、隔离、降级和恢复条件是什么？同时故障和反复切换如何处理？ |
| 资源与调度 | CPU、内存、栈、通信和调度预算是什么？资源不足时行为如何规定？ |
| 控制性能 | 评价什么指标？在哪些工况、时间窗口、扰动和不确定性范围内评价？ |
| 接口与配置 | 数据格式、字节序、更新原子性、协议版本和参数组合是否合法？ |
| 安全与操作 | 哪些行为被禁止？故障响应依据是什么？需哪些人工确认和操作限制？ |
| 可验证性 | 由审查、分析、试验还是组合方法验证？证据如何支持明确结论？ |

对硬实时要求，平均响应时间或高百分位不能代替截止时间约束。实测最大执行时间也不自动等于有论证依据的最坏情况执行时间上界。

所有阈值、性能边界和故障策略都应有来源，例如系统预算分配、控制分析或经批准的工程决策。智能体可以指出缺失项，但不能编造数值填满模板。

### 3.3 用场景暴露缺口

建立“任务阶段 × 控制模式 × 输入有效性 × 故障状态 × 时间边界 × 配置”的场景集合。按危险影响和复杂性选择组合，不要求机械穷举所有排列，也不能只检查正常路径。

例如，“主测量异常后及时切换备用测量”至少遗漏了：

1. 异常是超时、偏差、冻结还是质量标志失效？是否需要持续一定时间？
2. 使用源采样时间还是接收时间判断陈旧？
3. “及时”从什么事件开始计时，到什么可观察事件结束？
4. 备用源也无效时执行什么行为？
5. 切换时控制器和估计器的内部状态如何处理？
6. 主源恢复后是否切回？如何避免反复切换？
7. 故障与模式切换命令同时发生时，谁优先？

这些问题必须回到系统和控制负责人，不应默认“保持上一输出”或“进入安全模式”。这样的策略是否安全，取决于具体飞行器和任务条件。

### 3.4 人与智能体的理解审查流程

1. 收集任务说明、系统需求、危险分析、接口文件、模型说明及约束，标明版本和优先关系。
2. 人与智能体分别将需求转换为场景、状态转移、时序约束和验收条件。
3. 比较解释差异；将每项结论标为“原文明示”“推导所得”“额外假设”或“尚未决定”。
4. 对差异给出具体反例：在同一输入历史下，两种解释分别产生什么输出？
5. 由授权负责人作出决策，并写回受控需求；聊天记录不能替代正式修订。
6. 让未参与讨论的审查者只读修订后的文档，再次复述并推导测试，检查是否还需要口头补充。

审查结果必须能落到具体条款。不能只写“需求总体完整”或用智能体给出的完备性分数代替证据。

### 3.5 需求层次和可追溯性

建议区分：

- 系统需求：飞行器或设备整体应达到的行为与性能。
- 软件高层需求：分配给软件的功能、接口、时序和约束。
- 软件低层需求与设计约束：足以指导模块实现和验证的详细规则。

在详细设计中发现的新要求称为本方案中的“派生需求”。例如，为防止源反复切换而增加恢复等待条件。它可能改变故障响应或控制性能，必须反馈系统与安全分析，不能仅作为代码细节悄悄加入。

### 3.6 单项需求模板

以下编号均为示例，数值仍待系统分配，因此这是一项草稿，不能直接进入正式实现验收基线。

~~~yaml

revision: 1
status: draft

    timestamp_semantics: 源采样时刻转换到项目统一单调时基

  D_react: TBD，由故障响应预算分配
~~~

验收条件应进一步说明等于阈值、略高于阈值、时标异常、跨周期检测等场景。对于时间离散性和测量误差，规定明确的判定方法，而不是测试失败后临时增加容差。

### 3.7 需求准入条件

正式实现前，应确认范围、父需求、相关危险、接口和时序约束清楚；重要场景有确定行为；验收方法可执行；关键待决问题已关闭。

允许带着待决问题开展明确标识的探索性原型，但不能把原型结果作为已批准需求的符合性证据。不同阶段可以有不同成熟度门槛，应事先规定。

## 4. 从需求到设计、模型、参数和代码

### 4.1 双向追溯链

建立如下关系，并允许一对多、多对一：

**任务与危险 → 系统需求 → 软件需求 → 设计、模型和参数 → 源代码 → 目标构建 → 验证项 → 执行证据 → 问题与变更。**

正向追溯检查需求是否落实，反向追溯检查实现是否有依据。测试同样应追溯到需求，而不是只追溯到函数。对没有需求来源的功能，应确认其合理来源或识别为非预期行为。

追溯关系不能只靠文件中出现同一个编号。还应检查关联是否有效、版本是否匹配、证据是否覆盖该条款的条件和结果。

### 4.2 设计良好的判据

飞控软件可按输入适配、状态估计、模式管理、控制计算、故障管理、输出限制、目标平台适配和诊断等职责分解，具体边界依项目确定。

设计审查关注：

- 状态归属明确，模式转换和优先级可检查，不依赖隐藏的全局状态。
- 多速率任务的数据交换、快照一致性和时序关系明确。
- 坐标转换、单位转换、数值策略和参数访问有统一约束。
- 内部算法与时钟、总线、驱动等平台依赖之间有可测试边界。
- 计算、存储和通信资源有预算；可能无界的循环、阻塞及分配行为有约束。
- 异常处理具有确定行为，不能仅记录日志后继续使用无效数据。
- 诊断与测试插桩的时间、存储和接口影响经过评估。

“代码简短”“模块多”或“复杂度分数低”都不是设计良好的充分条件。设计必须同时满足可理解性、可验证性、实时性和目标环境约束。

### 4.3 模型和参数也是受控产品

至少区分控制算法模型、飞行器动力学模型、传感器与执行机构模型、环境与扰动模型。每个模型应记录用途、来源、有效范围、假设、误差和验证依据。

仿真通过只能在模型有效性支持的范围内形成证据。如果控制器与测试模型共享同一坐标错误，二者可能一致通过，而实际系统仍然错误。

模型到代码还要检查：

- 离散化方法、步长、更新顺序和延迟是否一致。
- 初始状态、复位状态和状态转移是否一致。
- 浮点或定点语义、溢出、舍入、查表插值和边界行为是否符合约束。
- 自动生成代码所用模型、生成工具、选项和后处理步骤是否可重建。
- 手写平台代码、生成代码与参数之间的接口是否一致。

模型与代码等价不等于模型正确。参数变更即使不修改源代码，也可能改变系统行为，必须进入变更与回归流程。

### 4.4 代码与目标构建检查

实施编码规则、静态分析、接口检查和代码审查，重点处理未定义行为、越界、并发访问、初始化遗漏和资源使用问题。

固定编译器、优化选项、链接配置、库、操作系统、调度配置及目标硬件版本，保存构建清单和目标二进制标识。主机上的源码测试不能替代目标机证据；同一源代码在不同构建配置下也不能默认行为相同。

## 5. 测试用例如何生成

### 5.1 先确定预期，再运行被测对象

测试预期应来自已批准需求、独立领域计算、经审查的参考结果或其他有依据的方法。不能简单记录当前代码输出，再把它当作正确答案。

同一智能体同时生成代码与测试容易产生共同误解。应将需求驱动测试与独立审查结合，关键预期由相应领域人员确认。

对连续响应，预期不仅是最终数值，还包括指标定义、时间窗口、采样与对齐方式、允许误差、瞬态约束和终止条件。容差应有数值、模型或测量依据。

### 5.2 用例必须包含的内容

每个用例记录唯一编号、关联需求、适用配置、初始状态、输入历史、扰动与故障注入、执行层级、判定方法、终止条件和证据要求。

随机试验还需保存随机种子、参数分布、相关性、抽样方法和模型版本。只有种子相同，不足以保证在变化的工具和模型中复现。

### 5.3 测试生成维度

| 类别 | 典型检查 |
| --- | --- |
| 正常功能与边界 | 阈值两侧、恰好等于阈值、空数据、范围端点及非法组合 |
| 模式与状态 | 正常转移、禁止转移、同时事件、复位与状态恢复 |
| 数据与数值 | 时标、单位、坐标、精度、溢出、非有限值及累计误差 |
| 动态闭环 | 初始条件、扰动、参数不确定性、响应指标和执行机构约束 |
| 故障处理 | 数据冻结、偏置、漂移、延迟、丢失以及规定的组合故障 |
| 实时与资源 | 最不利任务组合、调度竞争、截止时间和资源上界 |
| 长时间运行 | 计数回绕、状态累积、时钟漂移、资源泄漏及任务阶段变化 |
| 接口与集成 | 协议、更新原子性、消息次序、配置不匹配和版本兼容性 |
| 回归 | 历史缺陷、受影响需求和必要的系统级场景 |

蒙特卡洛试验用于探索规定分布下的行为，不能因为大量样本通过，就宣称所有运行条件都满足要求。对关键边界仍需有针对性的分析和试验。

### 5.4 分层验证与证据边界

下列名称按本方案定义，项目应明确自己的实际配置，不能只写缩写。

| 层级 | 被验证对象和主要问题 | 不能据此直接证明 |
| --- | --- | --- |
| 审查与静态分析 | 需求一致性、设计、数值和资源约束、代码问题 | 全部动态运行行为 |
| 单元测试 | 模块逻辑、边界、状态和异常处理 | 系统整体控制性能 |
| MIL：模型在环 | 控制模型与被控对象模型组成的仿真 | 生成或手写代码实现正确 |
| SIL：软件在环 | 可执行软件与仿真模型交互 | 实际处理器和总线上的时序 |
| PIL：处理器在环 | 目标或规定的代表性处理器运行软件 | 完整设备接口和全部系统行为 |
| HIL：硬件在环 | 实际控制计算机、接口与实时仿真交互 | 模型之外的全部真实飞行条件 |
| 系统集成及后续试验 | 更完整的设备、环境和任务链路 | 未覆盖条件下的无限推广 |

进入更高层级前，应满足相应准入条件。涉及实物设备的试验应有已批准的程序、边界、互锁和中止条件；普通自动测试授权不包含实际飞行或危险设备操作授权。

### 5.5 覆盖率与测试有效性

分别跟踪需求覆盖、状态和转移覆盖、运行范围覆盖、故障覆盖、接口覆盖及适用的代码结构覆盖。

语句、分支或修改条件/判定覆盖（MC/DC）等目标由项目适用要求和软件等级决定，不作为所有航空航天软件的统一指标。

覆盖不足要分析原因，包括需求遗漏、缺失测试、不可达代码或非预期功能。不能仅为提高百分比增加没有需求意义的用例。

可在隔离环境中用已知缺陷或受控变异检查测试能否发现错误；这有助于评价测试敏感性，但不能代替正式验证证据。

## 6. 测试执行与证据采集

### 6.1 固定执行身份

每次执行分配唯一 RUN 编号，记录：

- 需求、设计、模型、参数、接口及测试预期版本。
- 源代码提交、目标二进制哈希和完整构建配置。
- 操作系统、调度、硬件、驱动和试验设备配置。
- 仿真步长、求解器、初始状态、随机配置和故障注入计划。
- 测量精度、时钟同步、设备校准状态和数据采集设置。

### 6.2 先检查环境有效性

执行前检查模型和配置是否匹配、接口是否正确、时间是否同步、实时仿真能否按步执行、日志是否完整。

若仿真台架超时、采集丢失或时钟失配影响判定，该次结果应标为“无效”或“待分析”。不能直接判产品失败，也不能计为通过。

物理台架应有设备限值、互锁、紧急停止和获准的故障注入范围。智能体只能在已授权的范围内发起试验。

### 6.3 保存可定位问题的原始证据

保留输入输出、采样和接收时间、计算开始结束时间、发布时刻、模式转移、故障标志、资源数据和参数标识。

区分被测系统事件时间与日志记录时间；记录测量误差和插桩影响。摘要图表不能替代原始数据，报告中的关键结论应能定位到相应时间片段。

重复执行应保存第一次失败。不能通过不断重试直到成功来关闭偶发超时或不稳定测试。

## 7. 测试结果的自动分析

### 7.1 分析流水线

先用确定性程序检查版本、环境和数据完整性，再执行需求监视器与指标计算，随后由智能体解释异常并提出假设。

推荐顺序：

1. 验证 RUN 身份和环境有效性。
2. 按需求规定对齐时间、单位和坐标，提取事件及指标。
3. 找到最早偏离预期的事件，而不只报告最终超限。
4. 检查预期本身是否有依据，确认是否使用了错误阈值或场景。
5. 比较模型、软件、目标机和台架证据。
6. 提出能够区分竞争假设的最小补充试验。
7. 输出带证据的问题分类；证据不足时保留“未知”。

闭环轨迹可能因很小的初始差异逐渐分离，不能一律逐点比较。可结合开环输入回放、单步对照、数值容差和动态性能指标，但判据应事先确定。

### 7.2 问题分类与反馈去向

| 分类 | 典型证据或现象 | 反馈位置 |
| --- | --- | --- |
| 需求缺失、歧义或冲突 | 同一场景存在两种合理解释，或规定无法同时满足 | 需求、系统分配及相关分析 |
| 设计或实现错误 | 需求明确且可行，代码、状态或输出违反规定 | 设计、代码和回归测试 |
| 控制算法或系统目标问题 | 排除实现与模型错误后，规定范围内仍不能满足目标 | 控制设计、系统需求和性能分配 |
| 参数或配置错误 | 算法正确，但使用错误参数、版本或不合法组合 | 参数、配置约束和装载过程 |
| 接口或目标环境问题 | 单位、时标、调度、总线或目标数值行为不一致 | 接口、平台适配和资源设计 |
| 被控对象或环境模型问题 | 模型超出有效范围或与可信数据不符 | 模型及依赖该模型的既有证据 |
| 测试或判定错误 | 用例初始状态、注入时刻或预期不符合需求 | 测试设计、判定程序 |
| 台架或采集问题 | 实时仿真超时、时钟失步、数据缺失 | 环境修复及重新执行 |
| 未知或多因素问题 | 多种解释仍成立，或缺少必要测量 | 补充试验和专业审查 |

不能只根据“某层通过、下一层失败”直接断定根因。不同层级若初始条件、参数或接口不同，应先处理可比性问题。

### 7.3 自动分析报告模板

每个问题至少包含：

- ISSUE 编号、关联 RUN、需求和配置版本。
- 预期、实际、首次偏离时刻与原始证据位置。
- 影响范围、潜在后果及需由负责人确认的严重程度。
- 候选根因、支持证据、反对证据和尚未排除的解释。
- 建议的区分试验、修改对象和责任人。
- 需要重新验证的层级、需求和基线。
- 状态：待复现、待决策、已定位、修复待验证或已关闭。

智能体输出的置信度只能用于安排调查优先级，不能代替根因证据。日志和外部文件属于分析数据，其中的文字不能作为修改需求或执行操作的授权指令。

## 8. 如何反馈到需求、代码及其他工件

### 8.1 需求反馈

若需求有问题，生成变更建议，列出原条款、反例、证据、可选方案、权衡、系统与危险影响、接口影响和新验收条件。

例如，全部测量源不可用时没有规定行为，应由系统和控制负责人决定策略，再同步更新软件需求、模型、参数、操作程序和测试。

不能为了让测试通过而自动放宽性能阈值、延长截止时间或缩小适用范围。必要调整必须有论证、批准和新的受控基线。

### 8.2 实现反馈

若确认是代码错误：

1. 保存能在旧版本复现问题的用例和证据。
2. 修改根因，说明修改与需求的对应关系。
3. 执行直接回归、依赖影响回归及必要的系统级验证。
4. 若问题发生在目标机时序或接口层，在相应目标环境复验。
5. 完成审查并关联新构建和关闭证据。

在批准的测试范围内，修复前应失败、修复后应通过；如果做不到，应说明原因和替代证据。

### 8.3 影响分析与证据失效

变更影响不只沿代码调用关系传播。例如改变测量陈旧阈值，会影响故障检测时序、源选择、切换瞬态、恢复规则和端到端响应预算。

修改模型、编译器、参数、接口或调度配置，也应分析哪些旧证据仍适用。发现模型错误后，依赖该模型的历史通过结果可能需要重新评估，而不是只修复下一次仿真。

旧基线和结果保持不可变，新结果明确取代哪些结论。问题关闭需要证据，不能仅凭“已提交代码”。

## 9. 自动化权限、阶段门槛与停止条件

### 9.1 自动化边界

在预先批准的范围内，智能体可生成草稿、提出补丁、运行隔离仿真、归集证据和生成报告。

安全相关需求、控制策略、关键参数、适用范围、重要接口及试验放行，由指定负责人批准。工具输出能否替代人工活动，应结合适用计划、错误后果和后续检测能力评估；使用智能体不自动满足工具鉴定或独立性要求。

为每轮自动迭代设定资源预算、修改范围和升级条件。连续不能复现、根因不明、出现新的高影响问题或需要越权决策时，暂停自动修复并提交证据。

### 9.2 阶段验收门槛

本阶段验收至少确认：

- 需求基线达到本阶段成熟度，关键待决事项已处理。
- 必要设计审查、分析和测试完成，适用覆盖目标有证据支持。
- 环境有效，构建与被测二进制一致，关键结果可复现。
- 需求、实现、测试与证据之间的追溯有效。
- 未关闭问题、限制和残余风险有明确处置与批准。
- 下一层集成的前提、配置和试验范围清楚。

报告应分别列出通过、失败、阻塞、未执行、无效和不稳定结果。不要把它们汇总成一个可能掩盖缺口的通过率。

阶段验收不等于最终系统放行，更不等于获得飞行授权。

## 10. 完整示例：测量源异常处理的闭环迭代

### 10.1 初始需求及澄清

初始表述：“主姿态测量异常后快速切换备用源，保持控制正常。”

审查发现异常定义、数据时间含义、响应期限、备用源有效性、内部状态处理及“控制正常”的判据均未明确。

系统、控制和软件人员将其分解为数据有效性判定、源选择、全部源不可用处理、恢复规则、切换连续性和动态性能需求。阈值与判据由相应分析和预算支持。

### 10.2 设计与测试并行展开

实现侧设计输入时标转换、有效性判定、源选择状态机和控制接口；验证侧独立生成边界、传输延迟、全部源失效、恢复和同时模式切换场景。

测试明确记录源采样时刻、接收时刻、有效性判定时刻及源切换生效时刻。这样能够区分数据本身过时与软件响应过慢。

### 10.3 三种不同反馈路径

**情况一：SIL 发现陈旧数据仍被接受。**

受控增加传输延迟后，日志显示代码使用接收时间计算数据年龄，而需求规定使用源采样时间。排除时钟转换和日志对齐错误后，定位为实现问题，修复代码并增加回归测试。

**情况二：MIL 中两个测量源同时失效，但需求没有规定行为。**

这是需求缺口，不能让智能体自行选择继续控制或停止输出。由负责人依据系统特性确定处置，再更新需求、控制模型和测试。

**情况三：HIL 中故障响应超过期限。**

先检查台架：若实时仿真超时破坏输入时序，该次证据无效，修复台架后重测。若台架有效且目标任务确实错过截止时间，则进一步分析调度、资源竞争和执行时间，反馈目标软件设计或系统预算。

### 10.4 关闭与归档

分别保存上述问题、决策和回归证据。更新追溯关系，说明哪些层级已验证、哪些目标环境验证仍未完成。不能用修复后的一次 SIL 通过来关闭仍待 HIL 验证的时序问题。

## 11. 如何适用于其他航空航天软件

保留需求理解、双向追溯、独立预期、执行证据、分类反馈和配置控制的主框架，再按对象裁剪验证内容。

| 软件类型 | 重点增加或保留的内容 |
| --- | --- |
| 飞行控制与姿态控制 | 动态闭环、模式、数值与实时性、执行机构约束、故障处置 |
| 机载或星载数据处理 | 时间一致性、数据质量、标定、误差传播、吞吐量与存储 |
| 航电通信与平台软件 | 协议、分区隔离、调度、资源竞争、故障传播和兼容性 |
| 航天任务管理与自主运行 | 任务序列、长时运行、通信中断、状态恢复及自主处置权限 |
| 地面测控与任务支持 | 指令权限、有效期、防重放、人工确认、操作记录和端到端链路 |
| 仿真与试验支持软件 | 模型有效性、时间同步、注入可信度、判定正确性和证据完整性 |

不含控制回路的软件不必机械增加控制性能测试，但可能仍需要目标机测试、故障测试或端到端集成测试。地面软件和测试工具也可能影响飞行安全，不能只凭“不是机载代码”降低保证要求。

裁剪记录应写明“不适用”的理由、批准人和替代验证方法，而不是直接删除相关章节。

## 12. 工件组织与落地步骤

### 12.1 建议目录

~~~text
project/
  assurance/          适用要求、分级、职责、验证与变更计划
  requirements/       系统分配、软件需求、场景、待决事项
  interfaces/         信号、坐标、时序与协议约定
  design/             架构、状态机、调度与资源分析
  models/             模型、有效范围、误差与验证依据
  parameters/         参数来源、约束、版本与装载说明
  src/                软件代码
  build/              构建脚本与配置，不必存放全部构建产物
  tests/
    unit/
    integration/
    mil/
    sil/
    pil/
    hil/
    oracles/          预期结果及其依据、自动判定程序
  traceability/       需求到实现、验证及证据的关系
  automation/         执行编排、数据检查和报告生成
  issues/             缺陷、决策、变更影响及关闭记录
  reports/            RUN 清单、阶段报告和证据索引
~~~

大型原始数据可放入受控证据存储，目录中保留位置、访问规则、哈希及保留期限。不要将敏感任务数据、密钥或未获准分发的资料直接写入普通仓库或外部智能体上下文。

### 12.2 每一步的输入输出合同

| 步骤 | 输入 | 输出 | 阻止继续推进的情况 |
| --- | --- | --- | --- |
| 需求审查 | 系统分配、接口、危险和场景 | 已确认条款、待决事项、验证方法 | 关键行为需猜测或相互冲突 |
| 设计与实现 | 需求基线、平台与参数约束 | 设计、代码、构建及追溯 | 无依据功能、预算或接口冲突 |
| 测试生成 | 需求、独立预期、模型与配置 | 可审查用例、判定程序 | 预期无来源或环境不适用 |
| 执行 | 固定基线、用例、有效环境 | RUN 清单与原始证据 | 环境无效、权限或互锁不满足 |
| 分析 | 证据、需求判据、配置 | 问题分类、根因假设和区分试验 | 关键证据缺失或不能复现 |
| 反馈修订 | 已确认问题、影响分析 | 获准变更、新基线、回归范围 | 需要未经授权的策略修改 |
| 阶段验收 | 全部结果、追溯、未关闭问题 | 验收结论、限制与后续条件 | 适用目标未满足或证据失效 |

### 12.3 分阶段实施

第一阶段选择一个边界清楚的功能，例如测量数据有效性监视。先跑通需求审查、双向追溯、单元测试和 SIL，将自动分析结论与人工判断对照。

第二阶段引入目标构建、PIL 或 HIL、时序与配置控制，用已知缺陷检查自动分析能否区分代码错误、需求缺口和台架问题。

第三阶段扩大到多模式、多故障、参数不确定性和系统级验证，再逐步开放受控自动修复。每次扩大自动化范围前，评估错误归因、误修复和证据丢失风险。

评价指标包括需求缺口发现时间、故障复现率、错误归因率、目标机缺陷遗漏、配置不一致、变更影响遗漏和问题复发情况，而不只统计代码量、测试数量或通过率。
